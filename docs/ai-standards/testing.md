# Testing Standards

## Validation Is Mandatory

完成实现前，必须运行与改动范围相匹配的验证。

- 小改动跑最相关的测试：`cargo test -p <crate> <过滤词>`
- 完整验证：`just ci`（lint + 测试 + 文档）
- 会改变 API、CLI、后台任务、持久化、启动或部署行为时，补充**最高可行保真度的真实入口验证**（见下）

门禁失败时，先确认是不是本次改动引入的：在 `git archive HEAD | tar -x -C <临时目录>` 导出的干净副本里跑同一条命令，结果相同就是既有问题——交付说明里写明复现方式，另开任务处理，不混进当前改动。不要用 `git stash` 做这个对照（stash 栈在同一仓库的所有 worktree 之间共享）。

## Realistic Validation

测试分层要覆盖「逻辑正确」和「真实入口可用」两件事：

| 层级 | 在本仓库里的形态 |
|---|---|
| unit | 与代码同文件的 `#[cfg(test)] mod tests`：纯逻辑、边界、错误分支；用 `tpl-core` 的内存替身（`auth::testing`）代替端口实现 |
| integration | `crates/<name>/tests/*.rs`：走完整路由与中间件，替换掉慢/贵/不稳定的依赖（如 `crates/api/tests/auth_routes.rs`） |
| real entry | 账号服务真实进程：`just run backend` 或独立容器 `just accounts-up` 后用 `curl`；本地全栈 URL 由 `just run` 打印；真实 socket + 真实 PostgreSQL/Redis 的自动化测试在 `services/accounts/tests/http_end_to_end.rs`（`just test real`） |
| user flow | 真实浏览器：`just web-e2e`（`frontend-public/e2e/`、`frontend-admin/e2e/`），起真实的数据库、后端、前端，用 Chrome 走完用户可见的流程 |
| live | 仅在外部服务行为无法用本地替身证明时使用，且必须显式 opt-in |

规则：

- 不要求所有变更都上 live 外部服务，但必须说明最高可行保真度是什么。
- mock 可以用于慢速、昂贵或不稳定的依赖；关键边界本身要尽量保持真实：路由、配置加载、序列化、数据库迁移、启动装配。
- 需要凭据、沙箱账号或外部服务时，验证必须用环境变量显式开启，并记录无凭据时仍需通过的 fallback 验证。
- PRD 或规划任务必须写明真实入口、mock 边界、数据/环境需求、命令或人工流程，以及该验证是否阻塞验收。

## 前端验证

- 前端改动至少跑 `just web-check`（类型、lint、生产构建）；涉及**用户可见流程**（登录、注册、受保护页面、错误提示）时必须跑 `just web-e2e`，它走的是真实浏览器 + 真实后端，属于 `real user flow` 层
- 改**后端的接口契约**（字段名、返回结构、错误码、状态码）时，同步改 `frontend-public/lib/api/`、`frontend-admin/src/api/` 和 e2e，并重跑 `just web-e2e`：前端的类型是手写的，编译器发现不了与后端的契约漂移
- 截图或断言只验证到哪一层就写哪一层：组件预览、生产构建、真实用户流程不要混为一谈
- 断言要等待异步加载完成（`waitFor`）；「刚跳转完就立刻检查文本」是测试自身的竞态，不是前端的 bug，也不能用来掩盖前端的 bug

## 需要真实外部服务的测试

写成 `#[ignore = "原因"]` 的测试，默认 `cargo test` 不跑，用 `just test real`（只跑被忽略的）或 `just test all`（全部）显式开启。

- 连接串从环境变量读（`TEST_DATABASE_URL`、`TEST_REDIS_URL`），缺失就**失败并提示**，不要静默跳过——静默跳过等同于没有这条测试
- `just db-up` 启动本地 PostgreSQL / Redis（端口 5433 / 6390）
- 会写入真实数据库的测试必须自己清理，或使用独立的一次性 schema/库，不得留下残留数据

### 内存替身（`testing` feature）

`tpl-core` 提供 `auth::testing`（内存用户存储、内存会话存储、明文「哈希器」），只在测试或显式启用 `testing` feature 时编译；`tpl-api` 在 `[dev-dependencies]` 里启用它。**`PlainPasswordHasher` 不做任何加密，绝不能出现在生产依赖里。**

替身适合验证「规则」（校验、编排、HTTP 映射）；SQL、唯一约束、Redis 过期这类**只有真实服务才能证明**的行为，必须用 `#[ignore]` 的真实服务测试覆盖，不能用替身顶上。

## Test Double Boundaries

替身（fake、stub、注入的实现）可以替掉慢、贵或不稳定的依赖，但**不得替一个不受我们控制的外部系统凭空断言它的输出形状**。

- **替传输**（网络、时延、计费）：合法，数据形状仍由我们这侧的契约决定
- **发明契约**：替身手写出「外部系统应该长这样」的响应，却没有任何东西验证生产代码真的能引出这个形状——这不是测试，是把假设固化成了绿灯

规则：

1. 替身产出的数据若本应由外部系统（LLM、第三方 API、硬件）生成，必须另有一道检查把**生产侧的指令或 schema**与**消费侧的解码器**绑在一起，且词汇表从解码器常量派生，不要重抄一份
2. 替身不得是某段生产代码的唯一执行者：只有替身路径会绕开的代码（提示词构造、请求组装）必须有自己的用例
3. 缺凭据、缺配置或缺外部服务时，**停下来报告并交人补齐**，不得用替身顶上去再宣称完成了真实入口验证。正确结论是「未验证 + 阻塞原因」，而不是「通过」
4. 依赖「环境恰好没有某项配置」的跳过守卫等同于没有守卫；要在用例里显式构造出该状态，让用例在任何机器上都真的运行

## 不为可测性修改生产代码

不得为了让测试或负控能变红，往生产代码里加故障注入开关、失败模式、test-only 配置项、计数器或观测钩子。无法变红时记 `negative_control: not feasible — <原因>`。

（Rust 的 `#[cfg(test)]` 允许在测试编译时额外编译辅助代码，但它不应改变生产路径的行为。）

## 敏感信息

- 测试里不要出现真实凭据；用明显的假值
- 为「不泄密」写断言：例如 `Debug` 输出不含密码、错误响应不含内部原因（见 `config.rs`、`health_routes.rs` 里的例子）

## 守卫测试（Guard Tests）

守卫测试断言**仓库自身的约定**没被破坏（而不是业务逻辑）。本仓库目前只有一个：`services/accounts/tests/architecture.rs`（账号服务内部层依赖方向）；lint 由 clippy 强制。新增守卫测试时遵循：

- 守卫测试失败时，**修复触发它的源码或配置，不要改守卫测试本身让它通过**；仅当约定本身变更时才改它，并同步更新对应文档
- 每个守卫测试文件头标注「守卫测试（guard test）」，让 AI 代理第一眼识别「这是规则本身」

## Validation Evidence 的措辞

- 没有执行的验证，不能写成通过；写 `not run` 并说明原因
- 只验证到某一层，就写那一层：「单元测试通过」「集成测试通过」不能写成「端到端通过」
